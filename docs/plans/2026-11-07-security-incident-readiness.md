# Security hardening and incident readiness (2026-11-07)

The owner asked for research on hardening, admin switches to turn features off during an incident, a status page,
abuse detection, and a plan. This plan builds on what exists ([SECURITY.md](../../SECURITY.md),
[runbook](../runbook.md), [deployment](../deployment.md), the
[2026-11-04](../reviews/2026-11-04-security.md) and [2026-11-06](../reviews/2026-11-06-security-audit.md) reviews, the
[security plan review](../reviews/2026-11-06-security-plan.md), the [observability plan](2026-11-06-observability.md),
the [MCP plan](2026-11-07-mcp-server.md) and [BYOK key management](../byok-key-management.md)) and does not repeat what
already shipped.

Code facts were checked against `main` at `8202d50`. Advisory data comes from the GitHub advisory API
(`gh api /repos/<owner>/<repo>/security-advisories` and `/advisories?type=malware`), which is the primary source.
Everything else is cited inline, with full links in [Sources](#sources).

## TL;DR

- **Closest call this year:** the August 2026 malware releases of `cacheable@2.5.1`, `@cacheable/memory@2.2.1` and
  `keyv@6.0.0`. Our lockfile pins `cacheable@2.5.0` and `@cacheable/memory@2.2.0`, which ESLint pulls in through
  `flat-cache` with `^` ranges. The frozen lockfile and the 7-day cooldown are what kept the malicious versions out.
  Keep both.
- **Upgrades due 2026-11-10:** `next` 16.4.3 → 16.4.5 (seven advisories published 2026-11-03, none of them a strong
  match for how we run) and `better-auth` 1.7.14 → 1.7.16 or later (the two that applied to us are already
  mitigated). Both leave the cooldown on 2026-11-10. Neither needs an exemption.
- **The biggest real risks are in operations, not code:** account-wide tokens and the production DB password sit in
  plaintext files in the Codespace, there are no backups if production is on Supabase Free, and the logs an
  investigation needs are kept for 1 hour on Vercel and 1 day on Supabase Free.
- **Emergency controls:** one `controls` row in `app_settings` (validated, audited, 10 s cache) plus the
  `job_controls` pauses that already exist, an env-var hard off for each switch, and Vercel WAF rules as a
  break-glass that needs no deploy. Ten switches, specified below.
- **Status page:** Better Stack's free tier (10 monitors, 1 status page, custom subdomain), on
  `status.bhimraj.com.np`, monitoring `/api/health/ready`. Upptime on GitHub Pages is the fallback if the custom
  domain or subscribers turn out to be paid.
- **Abuse:** simple rules over data we already have (`ocr_rounds`, `ocr_calls`, `rateLimit`, `session.ip_address`,
  audit log), an Admin → Abuse view ranked by score, automatic throttles only, and nothing ever deleted
  automatically.

## Owner's personal security checklist

Only the owner can do these. They are in priority order, and the first five fit in one evening.

1. **Phishing-resistant MFA (passkey or hardware key) on every account that can reach production**, with SMS removed
   and recovery codes stored offline: GitHub; the Google account(s) behind Google Cloud, AI Studio (Gemini key) and
   the Google OAuth client; Vercel; Supabase; Cloudflare (R2, Turnstile, and DNS if it lives there); the `.com.np`

   have sat on disk in an environment that runs extensions, agents and `bun install`.
4. **Replace the GitHub fine-grained token before it expires on 2026-11-14**: one repository, the fewest permissions
   the task needs, and a 30-day expiry.
5. **Approve the 2026-11-10 upgrades** (`next` 16.4.5, `better-auth` ≥ 1.7.16).
6. **Spend caps:** a Google Cloud budget alert and quota cap on the Gemini project, a spend limit on the Anthropic

7. **Backups:** confirm the Supabase plan of `production-db`. If it is Free, approve the nightly dump in Phase 1 and

8. **Vercel hygiene:** check that every production secret is the **Secret** type (Vercel renamed Sensitive to

   account activity log; turn on the Bot Protection managed ruleset in **log** mode.
9. **GitHub:** a ruleset on `main` that requires CI (open decision 8), and check that secret scanning and push
   protection are on (Settings → Code security). The repository is public.
10. **Status page:** create the Better Stack account and add the `status` CNAME (Phase 0 below).
11. **Prune** the claude.ai connectors and plugins this project doesn't use (list under
    [Cognition item 9](#checklist-from-the-cognition-guide-nov-2026)), and install uBlock Origin in the browser used for

## Emergency controls (kill switches)

### Design rules

- **One store, two existing tables.** Feature switches live in a new `controls` key in `app_settings` (Zod-validated
  JSON, saved through `Settings.save`, which already writes `settings.<key>` to the audit log with `from`/`to` in the
  same transaction). Queue and provider pauses stay in `job_controls`. No new table.
- **Admin only, audited, with a reason.** The Admin → **Controls** page calls `requireAdmin()`, requires a reason
  (≥ 3 characters, as for bans) and, once [2FA](2026-11-06-passkeys-2fa.md) lands, a fresh session (`freshAge`). Each
  change is one audit row. Turning a switch on shows who did it, when and why, on every admin page.
- **Fast.** `controls` gets its own cache with a **10 s** TTL (settings use 30 s), dropped at once on the saving
  instance. Worst case across serverless instances: 10 s.
- **How it fails.** If the database can't be read, the reader serves the **last value it read**. With none (a cold
  instance during a DB outage) it serves the code defaults, which are "everything on". That is fail-open, on purpose:
  with the DB down, writes fail anyway, and failing closed would turn a DB blip into a full outage. Switches that must
  hold through a DB outage have an **env hard-off** (`CONTROLS_FORCE`, below) that wins over the DB and fails closed.
- **Enforced in core, not in `proxy.ts`.** The proxy has no DB access and only covers `/app` and `/admin`. Each
  switch is checked in the `packages/core` service that owns the action (one `Controls` Effect service), and in
  Better Auth hooks for auth paths. Routes stay thin adapters that map the refusal to a 503 with `Retry-After` and a
  message the UI shows.
- **Admins are never locked out.** Every switch exempts `/admin` and admin sessions, except "force sign-out", which
  keeps the acting admin's session.

### Break-glass when the admin UI is down

In order of speed:

1. **SQL in the Supabase SQL editor** (instant, within the 10 s cache). Saved in the runbook:

   ```sql
   -- Pause sign-ups and uploads, with a banner. Audit by hand: the app didn't make this change.
   insert into app_settings (key, value, updated_at)
   values ('controls', '{"signups":false,"uploads":false,"maintenance":{"on":true,"message":"Paused for maintenance"}}', now())
   on conflict (key) do update set value = app_settings.value || excluded.value, updated_at = now();
   insert into admin_audit_log (actor_email, action, target_type, target_id, reason)
   values ('<owner email>', 'settings.controls', 'settings', 'controls', 'break-glass via SQL: <why>');

   insert into job_controls (scope, paused, reason, updated_by) values ('queue', true, 'break-glass', '<owner email>')
   on conflict (scope) do update set paused = true, until = null, updated_at = now();

   delete from session;  -- force sign-out of everyone
   ```

2. **Vercel WAF custom rule** (seconds, no deploy, all plans; Hobby gets 3 custom rules, one of which can rate-limit).
   Deny `POST /api/receipts`, deny `/sign-up` and `/api/auth/sign-up/*`, or **redirect** everything to the status
   page (Vercel's "emergency redirect" guide). Keep one of the three rule slots free for this.
3. **Attack Mode** (seconds, free on all plans): a challenge on every visitor. Verified bots pass, Better Stack's and
   UptimeRobot's monitors included.
4. **Instant Rollback** (seconds). On Hobby it can only go back to the **previous** production deployment, and it
   keeps that deployment's old env values. After a rollback, auto-promotion stays off until undone.
5. **Env hard-off** (`CONTROLS_FORCE=signups,uploads,readonly,maintenance`, `MAINTENANCE_MODE=1`). Takes minutes:
   Vercel applies env changes only to **new** deployments, so this needs a redeploy (`production.yml` by hand, or
   Redeploy in the dashboard).
6. **Pause the Vercel project** (Settings → General → Pause, or `POST /v1/projects/{id}/pause`). Every visitor gets
   `503 DEPLOYMENT_PAUSED`. Resuming takes a few minutes and needs no redeploy. Use it when the app itself is the
   danger (data leaking out through a bug).
7. **Cut a dependency at its source:** revoke the AI key in the provider console (OCR stops), revoke the R2 token
   (uploads and images stop), or reset the DB password (everything stops).

stays static. Posting an incident on Better Stack and turning on the banner are two steps; the runbook lists both.

## Incident response runbook skeleton

Proposed as new sections of [runbook.md](../runbook.md): **Security incident** after **Compromised user account**,
and **Post-mortem** at the end. They reuse its existing **Leaked secret**, **Rollback** and **Secret rotation**
sections instead of copying them.

### Severity

| Level    | Examples                                                                                                                                                                                                 | Response                                                                              |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| **SEV1** | Data of other users exposed or likely exposed; a production credential (DB, auth secret, R2, Vercel/GitHub/Supabase token) leaked; an admin account taken over; malware ran on a machine holding secrets | Drop everything. Contain within 15 minutes. Start the breach clock (GDPR 72 h, below) |
| **SEV2** | AI key abused (spend), a mass sign-up or abuse wave, a vulnerability with no known exploitation, Resend domain blocked                                                                                   | Same day. Switches and rotation, no user notice unless data was involved              |
| **SEV3** | A suspicious event that may be nothing; an advisory in a dependency we don't exercise                                                                                                                    | Within a week, via a normal PR                                                        |

### First 15 minutes (SEV1)

1. **Write down the time**, what was seen and by whom, in a private incident note (a draft GitHub security advisory
   on the repo works: private, timestamped, and it can become the public advisory).
2. **Contain with switches**, not code: the preset that fits (Under attack / Data incident), or break-glass if the
   admin UI is suspect.
3. **Rotate the exposed secret first**, then the ones it could reach (order below). Redeploy once at the end.
4. **Revoke sessions:** force sign-out for everyone if the auth secret, DB or an admin account is involved. Otherwise
   only the affected users.
5. **Preserve evidence before it expires** (next section). Vercel Hobby runtime logs last **1 hour**.
6. **Post on the status page** ("investigating"), and turn on the banner if users are affected.

### Secret rotation order

Order by "what lets an attacker steal the rest", then by cost per hour. Use the runbook's rotation table for the
how-to of each.

1. **Control-plane accounts and tokens:** the owner's passwords and MFA on GitHub, Vercel, Supabase, Cloudflare and
   the registrar; then `VERCEL_TOKEN`, the GitHub fine-grained token, `SUPABASE_ACCESS_TOKEN` and Cloudflare API
   tokens. With any of these an attacker reads or replaces everything else.
2. **`DATABASE_URL` / `DIRECT_URL` password** (all data). Update Vercel and both GitHub environments.
3. **AI keys** (`GOOGLE_GENERATIVE_AI_API_KEY`, `ANTHROPIC_API_KEY`). They are abused for money within hours, and
   rotating them is cheap.
4. **`BETTER_AUTH_SECRET` / `BETTER_AUTH_SECRETS`.** Versioned rotation
   ([deployment.md](../deployment.md#rotating-the-auth-secret)) keeps stored OAuth tokens readable; then force
   sign-out. Data-encryption keys for BYOK credentials follow [BYOK key management](../byok-key-management.md) (KEK
   rotation re-wraps DEKs; `kekVersion`).
5. **R2 keys** (`S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`). Presigned URLs already issued expire within 10 minutes.
6. **`RESEND_API_KEY`** (phishing from our domain).
7. **OAuth client secrets** (Google, GitHub), then **`TURNSTILE_SECRET_KEY`**.

Then one redeploy, and the smoke test.

### User notification and legal timelines

- **GDPR (EU users):** notify the supervisory authority **without undue delay and, where feasible, within 72 hours**
  of becoming aware, unless the breach is unlikely to risk people's rights (Art. 33(1)). Information may follow in
  stages (33(4)). Notify the users themselves without undue delay when the risk is **high** (Art. 34(1)), unless the
  data was unintelligible (for example encrypted) or the risk has been removed (34(3)). **Document every breach,
  notified or not** (33(5)): keep a breach register in the private advisory notes. Our vendors (Vercel, Supabase,
  Cloudflare, Google, Anthropic, Resend) must tell us without undue delay as processors (33(2)).
- **Nepal (Individual Privacy Act, 2075 / 2018):** the sources found describe **no general breach-notification duty**
  for private companies, and no data protection authority. This rests on law-firm commentary, not the Act's text:
  **verify with Nepali counsel.**
- **India (DPDP Rules 2025):** notified in November 2025. Breach notice to the Board and to users (Rule 7) applies
  from a later phase, reported as 2027-05-13. **Verify** before relying on it.
- **Regardless of law:** if another user's receipts were readable, tell the affected users plainly what was exposed,
  when, what we did and what they should do.

**Admin → Abuse view.** One table of flagged users, ranked by a score (the weighted sum of the rules above over the
last 7 days). It is computed by SQL on page load, so it needs no new table. Each row shows its evidence (counts,
sample `ocr_calls` kinds, shared IPs, bounces), and offers one-click actions, all audited: **warn** (email),
**throttle** (per-user limit), **suspend uploads**, **ban** (existing), **hold content** (hide, keep). **Delete
content** is a separate, confirmed action. A **dismiss** writes `abuse.dismiss` to the audit log and hides the row for
30 days. Per-user restrictions need one `restriction` field on `user` (`none | throttled | uploads_suspended`, with
an expiry; `input: false`), which is a migration.

**False positives:** every automatic action expires (7 days) and tells the user why, with a reply-to address for
appeal. Throttles never touch data. The reviewer sees the evidence before banning.

**Build first:** (1) Resend webhooks and suppression, plus pausing non-essential mail near the quota (protects
sign-up); (2) the `auth.sign_in_failed` event and per-email sign-in failure limit; (3) the disposable-domain check;
(4) the Abuse view with throttle and suspend; (5) `documentType` from the model, which needs a benchmark check that
it doesn't hurt extraction.

### Pre-launch pentest checklist

Run against staging with test accounts, using the `security-reviewer` agent plus manual checks:

- Workspace isolation on every `/api/*` route and server action, with two users and a removed member (the `receipts.int` tests cover the core paths; repeat over HTTP).
- Auth: account enumeration on sign-in, reset and sign-up; reset-token reuse; OAuth state; email-change flows; the session after a password reset, ban and sign-out-all.
- Admin: every action as a non-admin; impersonation boundaries; CSRF on server actions (`Origin: null`, the class behind CVE-2026-27978).
- Uploads: magic-byte bypasses, polyglot files, PDF page-cap evasions (known list), oversize and slow bodies, HEIC.
- Rate limits: IPv6 rotation (GHSA-p6v2, fixed in our version), parallel bursts against the quota lock.
- Headers and CSP from outside; `/api/health` output (commit only); `robots`/`noindex`; directory and file probes.
- The Supabase Data API with the anon key: every table refused.
- Kill switches: each one on, each one off, and break-glass from SQL.
