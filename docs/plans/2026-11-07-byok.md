# Bring your own AI key and storage

_Plan · 2026-11-07 · revised the same day (admin controls) · status: proposed, nothing built_

> **Revision 2026-11-07: admin controls.** The owner's new requirements: default keys come from env **or a site key
> store in Admin → Settings** (several keys per provider); workspaces can add their own keys, **on by default**; a
> workspace can hold at most a few keys (2–3), set globally and **overridable per workspace**; an admin can **turn
> own keys off for one workspace**; own storage comes later on the same machinery; and **Groq** joins as a provider
> so people can bring a free key. What this revision changes: the request/approve flow for AI keys is gone, and
> storage gets an admin switch instead of a request state machine (§2.1, §7.0); "one key per provider" becomes an
> ordered list of up to N keys per workspace (§3, §4.2); every limit lives in the plan-limits table with
> per-workspace overrides, one precedence rule (§4.1); site keys and workspace keys share one table (`scope`); a
> disabled workspace's keys are **suspended and kept sealed, never deleted** (§4.4); admin pages gain key visibility
> and controls (§6.3); and the kill switch and an admin disable now route receipts to the platform chain _visibly_
> rather than refusing uploads, which restates "no silent fallback" more precisely (§4.3). Owner decisions, old and
> new, are in §11. Sections 7 and 9 (storage, encryption) stand as written.

A workspace can read receipts with **its own AI provider keys** (Google Gemini, Anthropic Claude, Groq), and later
keep receipt files in **its own S3-compatible bucket** (Cloudflare R2 recommended). Own AI keys are self-serve on
every plan and on by default, within a per-plan key limit that a platform admin can raise, lower or switch off per
workspace. Own storage is off by default and switched on per workspace by a platform admin. AI keys come first:
simpler, more asked for, and no server-side calls to customer-chosen hosts.

This plan replaces [`docs/byok-key-management.md`](../byok-key-management.md) (July, written for Clerk, per-user
keys). The implementing PR should mark that page as superseded.

## Summary

- **Owner of the key: the workspace.** Only the workspace **owner** can add, replace or remove a key or bucket;
  workspace admins see status and can run the check (pushback on "owner/admin", §5.3). Platform admins can
  suspend, never read or add.
- **One key table, two scopes.** `ai_keys` holds **site** keys (added in Admin → Settings, several per provider,
  with env keys shown beside them as read-only rows) and **workspace** keys. Same sealing, same check, same
  statuses, same audit. Storage credentials follow in phase S with the same shape.
- **Keys per workspace: an ordered list, not one per provider.** Up to the plan's key limit (recommended Free 2,
  Pro 3, hard cap 10 in code). Two keys of the same provider are allowed (rotation, a free Groq key next to a paid
  one). The list is the workspace's reading order; a failed key falls through to the next **workspace** key, never
  to a site key.
- **Limits in one place.** `byokMaxKeys` and `byokReceiptsPerDay` join `receiptsPerDay`, `receiptsPerMinute`,
  `batchMax`, `workspaces` and the members plan's `members` in the plan-limits table. A per-workspace override row
  (`workspace_overrides`, nullable columns, null = inherit) can change any of them and can switch own keys off.
  Precedence: kill switch → workspace override → plan → code default (§4.1).
- **Models: the existing allowlist** (`packages/ai/src/models.ts`), with Groq's vision models added behind a
  benchmark (§1.6). No custom base URLs, no OpenAI-compatible hosts, no Vertex/Bedrock in v1.
- **Encryption: envelope encryption** with Node's built-in `crypto` (AES-256-GCM, a per-row data key wrapped by a
  versioned key-encryption key in `DATA_ENCRYPTION_KEYS`), not the auth secret. Rotation re-wraps data keys from a
  job. Admin sees counts per version (§9). The site key store needs this too, so phase K comes first either way.
- **Check before saving:** the `checkProvider` from Admin → Check connections (being built), extended to take an
  explicit key. Storage reuses its storage check (write, read, delete a test object).
- **No silent fallback, stated precisely:** which keys read a receipt is decided when the upload is accepted and
  never changes mid-round. A failing workspace key fails the receipt with a clear reason; it is never retried on a
  site key. Routing moves to the platform chain only by a **human action** (owner removes the last key, admin
  switches own keys off, admin pauses the feature), and every such move is shown in Settings, emailed to the owner
  and audited (§4.3).
- **Quota:** own-key reads don't count against the daily plan quota or `OCR_DAILY_CAP`, but keep the per-minute
  limit and the plan's own-key ceiling (our storage, compute and database still pay, §4.5).
- **Ledger:** every call records `key_source` (`platform` or `workspace`) and `ai_key_id`. The customer sees
  estimated cost for their own-key calls; platform spend and caps leave them out.
- **Disabling keeps the keys.** When an admin switches own keys off for a workspace, its keys are marked suspended,
  stay sealed, and come back when the admin switches them on again. Only the owner deletes a key (or the workspace
  deletion does). Suspended keys are purged after 90 days with a warning email (owner decision 4).
- **Estimate:** about 13 engineer-days for own AI keys and the site key store (including 3 for the shared
  encryption and rotation work), then about 7 for own storage (+2 for moving existing files). No new dependencies.

### 1.2 Effect on Free and Pro

Today the plan quota is the only thing Pro sells beyond limits. If Free could use its own key without quota, Free
would become unlimited and Pro would lose its point. With own keys on by default for every plan (revision), the plan
table carries the difference instead of a gate:

- **Free:** can add up to `byokMaxKeys` keys (recommended 2) and read up to `byokReceiptsPerDay` on them (§4.5).
  Storage is locked with "Available on Pro". Setting Free's key limit to 0 in Admin → Plan limits turns own keys
  off for Free entirely (the §1.4 option (c)); the Settings copy then says "Available on Pro".
- **Pro:** more keys (recommended 3) and a higher own-key ceiling. Own-key reads skip the daily count.
- Storage in your own bucket is Pro and switched on per workspace by a platform admin: it moves files, not cost,
  and support time is the real price.

### 1.3 Pricing stance

**A Pro perk, not a separate tier, for now.** There is no billing yet (CEO review: "no way to pay"), so a BYOK tier
would be a price with nothing to charge it on. Revisit when billing ships: Cursor charges a per-token platform fee
on Teams even with the customer's key [C1], which shows that "own key" doesn't have to mean "free platform". If
BYOK users turn out to use a lot of storage and compute, add a small platform fee per receipt above an allowance
then, rather than now.

Don't put BYOK back on the landing page until it ships; the CEO review asked for those claims to be removed.

### 1.4 Free users at the limit: "use your own key to keep going"

The owner's idea: when a Free user hits the limit, offer an own key next to "Upgrade to Pro".

**For it.** We pay no model cost for those reads. An engaged user who would otherwise leave (often mid-batch: a
shoebox at month end) keeps going and keeps their receipts with us. Setting up a key is a step towards trusting the
product with more, which makes it an on-ramp.

**Against it.**

- **It eats into Pro** if Pro's main value is "more reads": today Free is 20 a day and Pro 1,000 a day
  (`DEFAULT_PLANS`), and that gap is nearly all Pro sells.
- **Support.** Non-technical users will get stuck on Google Cloud billing (project, billing account, "Free" vs
  "Paid" key). That's exactly the ticket we can't fix for them.
- **The free-tier data problem lands on Free users most.** The users least likely to link billing are the ones who
  will paste a free-tier Gemini key, whose content Google may use to improve its products [G1]. Free-tier keys also
  have low rate limits, so more failed receipts.
- **Same security for more keys.** Every stored key needs the full treatment in §5 and §9, whatever the plan pays.
  More keys, more support for "my key stopped working".
- **It's not free for us.** Each own-key read still costs R2 storage and writes, a job, Vercel function time and
  database rows. Small per receipt (R2 lists about $0.015 per GB-month and $4.50 per million writes, third-party
  [R3]; a receipt is about 500 KB), but unbounded without a cap. **There is no storage limit today** (CEO review), so
  Free own-key reads would be unlimited storage on our bucket.
- **Abuse.** Free accounts cost nothing to create, so "own key, unlimited" invites people to use us as free
  storage and processing. Sign-up has Turnstile, which slows that down without stopping it.
- **It conflicts with "Pro-gated with approval".**

**Options.**

| Option                                                                                   | Pro's value kept                                | Cost to us                            | Support | Verdict                     |
| ---------------------------------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------- | ------- | --------------------------- |
| (a) Free own key, no approval, no read cap (per-minute and abuse limits, a storage cap)  | Weak: reads are unlimited for anyone with a key | Storage grows unbounded until the cap | Highest | No                          |
| **(b) Free own key, no approval, with a monthly own-key cap** above Free, well below Pro | Yes                                             | Bounded                               | Medium  | **Recommended**             |
| (c) Own keys on Pro only                                                                 | Strongest                                       | Lowest                                | Lowest  | Safe, but loses the on-ramp |

**Recommendation: (b)**, with these numbers to start (all in the `plans` setting, admin-editable):

- Free own-key reads: **300 a month** per workspace on top of the normal Free allowance. Enough for a month-end
  batch; not enough to run a bookkeeping practice on Free.
- Pro own-key reads: the fair-use ceiling (§4), 2,000 a day.
- **A storage cap ships first** (for example Free 1 GB or 2,000 stored receipts), because the cost that stays ours is
  storage.
- Self-serve on every plan is now the default (revision), not a consequence of (b): the plan table's key limit and
  own-key ceiling are the only gates, a platform admin can switch own keys off for one workspace (§4.4), and the
  kill switch covers all.

**What Pro then sells:** 1,000 platform reads a day instead of 20 (no key, no Google account), team seats (3 vs 10 in
the [members plan](2026-11-06-members-admin-plan.md)), 5 workspaces instead of 1, the larger own-key ceiling, own
storage, more storage, higher MCP limits ([MCP plan](2026-11-07-mcp-server.md)), and later priority in the queue,
accounting exports and integrations. "No setup, no second bill" is itself the Pro pitch for most users.

**Limit-reached copy** (banner on upload and the 429 message):

> **You've read all 20 receipts for today.** Free resets at 00:00 UTC.
>
> **Upgrade to Pro**: 1,000 receipts a day, team seats, your own storage. [Upgrade]
>
> **Or use your own AI key** (Google, Anthropic or Groq) and keep going on Free (300 extra receipts a month). The
> provider bills you, not us. [Set up a key]

Wording follows the current quota message (`quotaMessage`), and changes with it if limits become monthly. When the
own-key allowance is also used up: "You've used this month's 300 own-key receipts on Free. Upgrade to Pro to keep
going."

**Guided setup, three steps** (a help page in the style of
[production-environment.md](../production-environment.md#gemini), Gemini through AI Studio as the default because it's the
quickest):

1. **Create a key.** In [Google AI Studio](https://aistudio.google.com): **Get API key → Create API key**, in a new
   or existing project.
2. **Turn on billing for that project** (Cloud Console → **Billing** → link an account) so the key list says
   **Paid**, not Free. Otherwise Google may use your receipts to improve its products. Optional: restrict the key to
   the Generative Language API, and set a budget alert.
3. **Paste it here and press Check.** We confirm it works and which models it can use, then you pick one and save.

Claude keys get the same three steps (Console → API keys, add credit, paste), linked as "Prefer Claude?". Groq keys
take two (console → API Keys → Create, paste; the free tier needs no billing), linked as "Have a Groq key?" (§1.6).

### 1.6 Groq: a free key to bring

Groq serves open-weight vision models (the Llama 4 Scout and Maverick family at the time of writing; ids to confirm
on the `feat/groq-provider` branch) on a free tier with no card and per-key rate limits, and a paid tier with list
prices. It's the provider that makes "bring a free key" true for a Free user, so it joins the allowlist with these
rules:

- **Allowlist like the rest.** A Groq model is an `OCR_MODELS` entry with the **paid-tier** list price (so the
  customer's estimated cost is an upper bound; the Settings line says "may be free on your tier") and a benchmark
  result on the receipt set before it's offered. Structured-output support differs by model; the benchmark decides
  `schemaMode`, as it did for Flash-Lite.
- **Workspace keys first, site chain later.** Offer Groq to workspaces as soon as the benchmark passes. Don't put a
  Groq free-tier key in the site chain: its rate limits are per key and sized for one developer, not a service. A
  paid Groq key in the site store is the admin's call, like any provider.
- **Expect `rate-limited`.** Free-tier limits are low, so Groq keys will trip the per-key cooldown more than
  others (§4.8). The failing-key copy names the provider's limit, and the job retries as it does today. Two Groq
  keys in one workspace are allowed within the key limit, but we **don't round-robin** across keys to stretch a
  free tier: the second key only serves when the first is cooling or rejected. Pooling many free keys is what most providers'
  terms forbid, and the key limit keeps it small.
- **Data terms.** Groq's free-tier data-use terms are not checked in this revision. Before Groq is listed, read
  them and, if the free tier allows training on inputs, add the same confirm sentence Google gets ("I'm using a
  paid plan").
- **Redaction.** Add Groq's key prefix (`gsk_`) to the key-shape denylist in §5.2.

## 3. Data model

One migration after the baseline, **expand-only**: new tables and nullable or defaulted columns. Nothing existing
is renamed or dropped. Old code runs against it unchanged, so it can be applied before the deploy.

### New tables

```ts
/**
 * A provider key, sealed. scope 'site': added by a platform admin in Admin → Settings and used by the
 * admin's OCR chain. scope 'workspace': added by a workspace owner. Never readable in plaintext from
 * the database.
 */
ai_keys {
  id uuid pk              // generated in the app before sealing: it's part of the AAD
  scope text              // 'site' | 'workspace'
  organization_id text    // fk organization on delete cascade; null iff scope = 'site'
  provider text           // 'google' | 'anthropic' | 'groq'
  label text              // ≤ 40 chars, shown in lists: "Finance project", "Groq free"
  model text              // workspace keys: the allowlisted model this key reads with. Site keys: null (the chain step names it)
  position smallint       // order within its scope: the workspace's reading order; site keys per provider
  sealed text             // v1.<kek>.<wrapped DEK>.<nonce>.<ciphertext+tag>, see §9; null once removed
  kek_version smallint    // copy of the version in `sealed`, for counts and the re-wrap job
  last4 text
  fingerprint text        // HMAC of the plaintext under its own versioned secret: same key in two places, §5.2
  status text             // 'active' | 'failing' | 'removed'   (the provider's verdict; 'removed' keeps the row for audit)
  suspended_at timestamptz, suspended_by text fk user set null, suspended_reason text   // an admin's hold; null = not held
  last_checked_at, last_ok_at, last_error_kind text, last_error_at
  created_by text, created_at, updated_by text, updated_at, removed_at
  check ((scope = 'site') = (organization_id is null))
  check (scope = 'site' or model is not null)
}
// Effective state, in one core function: removed → gone from lists; suspended_at set → "Suspended";
// else status. Suspension is its own column so an admin hold doesn't erase the provider's last verdict:
// re-enabling a key that was `failing` shows it failing again, not falsely active.
// Env keys (`OCR_PROVIDERS[].keyEnv`) are not rows: Admin → Settings lists them as read-only rows
// computed at render (provider, last 4), and their fingerprint is computed in memory for §5.2.

/** Per-workspace exceptions to the plan table. Null = inherit from the owner's plan. At most one row. */
workspace_overrides {
  organization_id text pk  fk organization on delete cascade
  byok_ai boolean          // false = own keys switched off by a platform admin (keys suspended, §4.4)
  byok_max_keys smallint   // 0 … MAX_BYOK_KEYS
  byok_receipts_per_day int
  members smallint         // the members plan's seat limit; same row, same pattern
  byo_storage boolean      // phase S: true = switched on by a platform admin
  note text                // admin's reason, ≤ 300 chars, plain text; shown to the owner when byok_ai = false
  updated_by text fk user set null, updated_at
}
// Columns mirror PlanPolicy fields and are added as needed; nothing else reads them directly (§4.1).
```

`PlanPolicy` gains `byokMaxKeys` (0 = own keys not available on this plan), `byokReceiptsPerDay` and `byoStorage`
(boolean), with the defaults in §4.1 and `MAX_BYOK_KEYS = 10` as the most an override may allow (like `MAX_BATCH`).
Mind the members plan's trap: new fields need defaults when a saved `plans` row is parsed, merged over
`DEFAULT_PLANS`, with a test, or every saved row fails validation.

```ts
/** A workspace's own bucket (phase S). */
workspace_storage {
  id uuid pk
  organization_id text  fk organization  on delete restrict   // purge job first, §7.4
  kind text             // 'r2' | 's3' | 'gcs'
  account_id text       // R2 account id; null otherwise
  region text           // 'auto' for R2, an allowlisted AWS region for S3
  jurisdiction text     // R2: null | 'eu' | 'fedramp'
  bucket text
  access_key_last4 text
  sealed text, kek_version smallint   // the access key id and secret, sealed together as JSON
  status text           // 'active' | 'failing' | 'retired'
  … suspension, check and audit columns as in ai_keys
}
```

`workspace_storage` rows are never hard-deleted while a receipt points at them: a receipt must always know where its
file is. Changing credentials for the same bucket updates the row; a different bucket is a new row, and the old one
becomes `retired` (still readable).

## 4. Limits, precedence and routing

### 4.1 Precedence: one rule for every limit

Every number a workspace lives under resolves the same way, most specific first:

| Level                | Set where                                                                                  | Who            | Wins when                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------ | -------------- | ------------------------------------------------------------------------------- |
| 1 Kill switch        | Admin → Settings → Own-key reading (`byok.ai` in `app_settings`: `on`, `paused`, `refuse`) | Platform admin | Anything but `on` beats everything below: no own-key rounds anywhere (§4.3, §8) |
| 2 Workspace override | Admin → Workspaces → _workspace_ → Limits and own keys (`workspace_overrides`)             | Platform admin | Any non-null column replaces the plan's value, for that workspace only          |
| 3 Plan               | Admin → Settings → Plan limits (`plans` in `app_settings`)                                 | Platform admin | The **owner's** plan (the members plan: quota and seats follow the owner)       |
| 4 Code default       | `DEFAULT_PLANS` in `packages/core/src/plans.ts`                                            | Engineer       | Nothing saved                                                                   |

`effectivePolicy(workspace) = { ...plans[ownerPlan], ...nonNull(override) }`, one function in core. Every check
(seats, quota, key limit, the Add key button) reads it; nothing reads the plan table or the override row directly.
An override may be **higher** than the plan (a Free workspace allowed 3 keys for a pilot) or **lower**; the hard
caps in code (`MAX_BYOK_KEYS` = 10, `MAX_BATCH`) bound both. There is no separate "global default" knob: the plan
row _is_ the global default, which keeps one mental model with seats and receipts.

Recommended numbers (all in the plan-limits form, §6.3):

| Plan limit                                      | Free | Pro   | Note                                                                                                                  |
| ----------------------------------------------- | ---- | ----- | --------------------------------------------------------------------------------------------------------------------- |
| Own AI keys a workspace can add (`byokMaxKeys`) | 2    | 3     | 0 locks the plan out: Settings shows "Available on Pro"                                                               |
| Own-key receipts a day (`byokReceiptsPerDay`)   | 50   | 2,000 | Per workspace. If plan limits go monthly (STATUS decision 3) Free becomes 300 a month, as §1.4 proposed               |
| Own storage (`byoStorage`)                      | off  | off   | Switched on per workspace by an admin (§2.1); the plan value is what Settings shows as "Available on Pro" vs "Ask us" |

Lowering a key limit below what a workspace holds removes nothing: the extra keys keep working and the owner can't
add another until under the limit (the rule the members plan uses for seats).

### 4.2 Key resolution when a receipt is accepted

Decided once, under the quota lock, in `ReceiptRepo.insert` / `claimRetry`, and recorded on `ocr_rounds` and in
the job payload. The job never re-decides.

1. **Effective policy** for the workspace (§4.1).
2. **Own keys?** If the kill switch is `on`, the override doesn't say `byok_ai = false`, and the workspace has at
   least one key whose effective state is `active` or `failing`: a **workspace round** (`key_source =
'workspace'`). Its chain is the workspace's keys in `position` order, one step per key with that key's model;
   suspended and removed keys are left out. `failing` keys stay in: a key the provider rejected an hour ago may be
   fixed now, and one success heals it. The own-key ceiling applies (§4.5); the plan quota doesn't.
3. **Otherwise a platform round** (`key_source = 'platform'`). The chain is the admin's OCR chain. Each step's key
   is the first usable **site** key for its provider: store rows in `position` order, then the env key. Usable =
   not failing, not cooling (§4.8), not suspended. A step whose provider has no usable key is skipped as
   `not-configured`, as today.
4. **Within a round**, a timeout, 429 or 5xx falls through to the next step of the **same scope**, as the chain
   works today. A 401/403 marks that key `failing` and also falls through, same scope. A round never crosses scope.
5. **Job runs** (`receipt.extract`): loads the key rows named in the payload (workspace id must match), opens them
   (§9), builds the chain. A workspace key removed meanwhile is skipped; if none are left, the round fails
   `not-configured` with the "key removed" message. Never a site key: the round wasn't counted against quota.

Which key served is recorded (`ocr_calls.ai_key_id`) for both scopes, so Operations can show failure rate per
site key as well as per workspace key.

### 4.3 "No silent fallback", restated

The rule protects two things: the customer's choice of processor (their receipts go where they said) and our bill
(a broken customer key must not become platform spend). Both are about **automatic, per-receipt** switching, so the
precise rule is:

- **Never at request time.** A round that starts on workspace keys ends on workspace keys, success or failure. No
  retry on a site key, no "we used ours this once".
- **Only by a human action, and visibly.** Three actions move a workspace to the platform chain: the owner removes
  their last key; a platform admin switches own keys off for the workspace (§4.4); a platform admin pauses own keys
  for everyone (kill switch). After each, the next upload is a platform round counted against the plan quota, the
  Settings page says so, the owner is emailed, and the audit log has the row.

This changes the original kill-switch behaviour (refuse own-key uploads). Refusing stopped every own-key workspace
during an incident. Routing them through the platform chain, counted and capped by the plan quota and
`OCR_DAILY_CAP`, keeps them working under the same terms as every other workspace, with the bill bounded by the
quota they'd have anyway. The owner keeps the choice: the kill-switch dialog offers "Pause and read with the
platform models (counts against plans)" as the default and "Pause and refuse own-key uploads" for an incident where
even that is wrong (owner decision 5).

### 4.4 Switching own keys off for one workspace

Admin → Workspaces → _workspace_ → **Own AI keys: Allowed / Off**, with a required reason (≤ 300 chars, shown to
the owner) and a confirm dialog. On **Off**:

| What                       | Happens                                                                                                                       |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Keys                       | Every key gets `suspended_at`, `suspended_by`, `suspended_reason`; `sealed` stays; `status` keeps the provider's last verdict |
| In-flight workspace rounds | Finish on the keys they were accepted with (the job already holds their ids). New uploads are platform rounds                 |
| Settings → Receipt reading | The disabled-by-admin state (§6.2) with the reason; Add key is gone, the list shows each key as Suspended                     |
| Owner                      | Email "Own AI keys were turned off for _workspace_" with the reason and the support address. Audit `workspace.byok.disable`   |
| Upload page                | One banner per session: "Receipts now use the platform models and count against your plan"                                    |

On **Allowed** again: suspensions clear, keys return to their previous status, a check runs on each, the owner is
emailed, the next upload is a workspace round. **Per-key suspend** (one key, not the switch) exists too, for a
single leaked or abusive key: same columns, same email, the other keys keep serving.

**Keep, don't delete**, because the admin doesn't own the key and can't put it back, the owner may be mid-dispute,
and "support deleted my key" is a worse ticket than "support paused my key". **But not forever:** a suspended key
nobody re-enables is a dormant secret. Purge `sealed` after 90 days of suspension (a job; email 7 days before; the
row stays as `removed` for audit). Owner decision 4.

### 4.5 Quota and caps (own-key rounds)

| Limit                                         | Platform rounds | Workspace-key rounds                                                                                    |
| --------------------------------------------- | --------------- | ------------------------------------------------------------------------------------------------------- |
| Per-minute burst (`receiptsPerMinute`)        | Yes             | **Yes**, same count (protects the queue and the database)                                               |
| Daily plan quota (`receiptsPerDay`)           | Yes             | **No**                                                                                                  |
| Own-key ceiling per workspace per day         | n/a             | **Yes**, `byokReceiptsPerDay` from the effective policy (§4.1), counted from `ocr_rounds`               |
| `OCR_DAILY_CAP` (global spend guard)          | Yes             | **No**: it bounds our spend. When it trips, own-key workspaces keep working, which is part of the value |
| Job queue fairness, PDF page cap, upload size | Yes             | Yes                                                                                                     |

`usedSinceSql` and `roundsSince` gain `r.key_source = 'platform'`. The per-minute count stays on all rounds.

### 4.6 Code shape

```ts
type KeySource =
  | { source: "platform" } // the admin chain; each step's key resolved from the site store, then env
  | {
      source: "workspace";
      steps: { keyId: string; provider: RegistryProviderId; model: ModelId }[]; // the workspace's keys, in order
    };
```

- Key **ids** travel in the round and the job payload; key **material never does**. The job opens each row (§9)
  and hands the plaintext to `Ocr.extract` in memory for that one call.
- `Ocr.extract(file, { keySource, keys, cooling })`. For `platform` it does what it does now, except `keys` comes
  from a `SiteKeys` resolver (store rows, then env) instead of env alone. For `workspace`:
  - the chain is one step per workspace key, `{ model: step.model, enabled: true, timeoutMs: DEFAULT_STEP_TIMEOUT_MS }`,
    in `position` order;
  - `keys` is built **only** from the workspace keys, keyed by key id, not provider (two keys of one provider stay
    distinct). `providerKeys` (env) and the site store are not read on this path at all.
  - `ready` checks the workspace keys, not env availability.
- A test pins both directions: a workspace run with env and site keys set must never send either (mock the provider
  factory and assert the key it got), and a platform run must never see a workspace key.

### 4.7 Clients and caching

- `registryFor` in `packages/ai/src/extract.ts` caches registries in a module `Map` keyed by `JSON.stringify(keys)`:
  plaintext keys as map keys, kept forever, growing with every workspace. Fine for two env keys; not for customer
  keys. **For workspace keys, build the provider per call and don't cache it** (`createGoogle` / `createAnthropic`
  are cheap; HTTP keep-alive is in the fetch layer, not the provider object). Platform keys keep the cache.
- `s3Client` in `packages/storage` has the same pattern (secret in the cache key). For phase S, key that cache by
  `workspace_storage.id` + `updated_at` instead, bound it (an LRU of, say, 200), and evict on replace or retire.
- No cache of opened keys across requests in v1. One key row read and one unwrap per job is cheap next to a model
  call. If KMS comes later, cache unwrapped data keys in memory for at most 5 minutes (§9.2).

### 4.8 Cooldowns

Provider cooldowns are keyed `provider:<id>` today. A 429 on a customer's key must not pause Gemini for every
workspace, and a platform cooldown must not hold a customer's job. Every key row, site or workspace, gets its own
scope, `key:<aiKeyId>`, in the same table; the env key keeps `provider:<id>`. This is also what lets a second site
key of the same provider take over while the first cools (§1.6: fall-through, not round-robin).

### 5.1 Ledger and cost

## 7. Bring your own storage (phase S)

### 7.0 Access (revision)

Own storage is the one feature that keeps a gate, because our server then calls customer hosts and the support
cost is real. The gate is the `byo_storage` override (§3) that a platform admin switches on from the workspace
page, after the owner asks through the feedback form (§2.1). The plan default is off on both plans; "Available on
Pro" is a copy decision from the plan's `byoStorage` value, not a separate check. Switching it off later keeps the
`workspace_storage` row (`retired`, still readable) and routes new uploads to our bucket, as §7.4 already says.
Everything below is unchanged.

### 7.1 What changes

New uploads in a workspace with an active `workspace_storage` go to that bucket under the same object key
(`users/<userId>/receipts/<receiptId>.<ext>`), and `receipts.storage_location_id` records it. The `Storage` service
in core resolves config **per receipt** (`location_id` → open credentials) instead of from env, for put, get,
remove and signed URLs. Extracted rows stay in our database.

### 7.2 SSRF: the server calls the customer's host

Put, get, delete and the check make server-side requests. Signing a URL makes no request.

- **No free-text endpoint.** The endpoint is built from a template:
  - R2: `https://<account_id>.r2.cloudflarestorage.com`, or `https://<account_id>.<eu|fedramp>.r2.cloudflarestorage.com`
    (jurisdiction form to verify in Cloudflare's docs), `account_id` must match `^[0-9a-f]{32}$`, region `auto`;
  - AWS S3: `https://s3.<region>.amazonaws.com`, region from a fixed list in code;
  - GCS (S3-interoperable XML API): `https://storage.googleapis.com`.
    Bucket names validated with the S3 naming rules; path-style addressing so a bucket name never becomes a hostname.
- **HTTPS only**, TLS verification on, no proxy from env.
- **Connect-time IP check:** a custom `https.Agent` with a `lookup` that rejects loopback, RFC 1918, link-local
  (incl. `169.254.169.254`), CGNAT `100.64/10`, IPv6 ULA and link-local, and IPv4-mapped forms of those, passed to
  the SDK's `NodeHttpHandler`. With templated public hosts this is defence in depth against DNS surprises. Test it
  under Bun too (the Docker image runs on Bun).
- **No redirects** (the S3 client returns them as errors; confirm with a test against a 301).
- **Timeouts:** connect 3 s, request 15 s. **Size limits:** refuse a `GetObject` whose `ContentLength` is above the
  upload maximum, and cap the stream as it's read.
- **Kill switch** stops all outbound calls to customer storage (§8).

### 7.3 Images in the browser and CSP

- `img-src` is already `'self' data: blob: https: http://localhost:9000` (report-only), so signed URLs to a customer
  bucket load today.
- **Recommendation: keep direct signed URLs**, and when `img-src` is tightened, list the template hosts
  (`https://*.r2.cloudflarestorage.com https://s3.*.amazonaws.com https://storage.googleapis.com`). That list is
  fixed, not per workspace, because the hosts are templated. Add `referrerpolicy="no-referrer"` on receipt images.
- **Proxying** the bytes through our app would hide viewer IPs from the bucket owner (who is the workspace owner, so
  not much of a privacy gain) at the cost of every image view going through a Vercel function: at about 500 KB a
  receipt, 1,000 views a day is about 15 GB a month of transfer plus function time. Not worth it for v1; revisit if
  CSP must be strict and the host list can't be.
- No CORS needed: the browser loads images with `<img>` and PDFs as downloads, and uploads go through our server.
  CORS only becomes necessary if uploads ever go straight from the browser to the bucket.

### 7.4 Lifecycle

| Event                             | Behaviour                                                                                                                                                                                                                                                                   |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Switching on own storage          | **New uploads only** in v1. Older receipts stay in our bucket and keep working                                                                                                                                                                                              |
| Moving existing files (later, S4) | A `storage.migrate` job kind: per receipt, copy, check SHA-256, flip `storage_location_id`, delete the source; idempotent and resumable. Same job moves files back to platform storage                                                                                      |
| Switching off own storage         | New uploads go to our bucket. Old ones stay readable from theirs while the credentials work                                                                                                                                                                                 |
| Deleting a receipt                | Delete the object in its location. If that fails (keys revoked), the receipt is still deleted and the user is told "the file may still be in your bucket"                                                                                                                   |
| Deleting a workspace or account   | A `storage.purge` job per location deletes our objects there (by prefix and by the receipt list), with retries; after that the `workspace_storage` row and its secret go. If it can't finish in 7 days, delete the secret anyway and email the owner the prefix to clean up |
| Their bucket gone or keys revoked | Receipt rows stay; images show "Image unavailable: your workspace's bucket didn't answer" and the location goes `failing` (owner emailed). Retries can't re-read and fail with that reason                                                                                  |
| File changed in their bucket      | Before re-reading for a retry, compare SHA-256 with `file_sha256`; on mismatch fail "the file in your bucket changed". The PDF page cap and size limit run again on every read                                                                                              |
| Backups                           | Theirs. We back up the database (extracted rows), not their bucket                                                                                                                                                                                                          |

### 7.5 Validation

Reuse the storage check from Admin → Check connections (being built), with explicit config: put
`receipt-ocr-check/<uuid>.txt` (a few bytes), get it and compare, delete it. Then an **unsigned** GET of the same
key before deleting: if it succeeds, the bucket is public; block saving with "This bucket is public; make it
private first". Errors map to: credentials rejected, bucket not found, missing permission (named: write, read or
delete), unreachable, timed out. The help text gives the minimal permission: object read and write on one bucket
(an R2 token scoped to that bucket, or an IAM policy with `s3:PutObject`, `s3:GetObject`, `s3:DeleteObject` on
`arn:aws:s3:::<bucket>/*`).

### 7.6 Privacy and terms

Images then live in the customer's account. We never keep copies, apart from the bytes in memory while uploading
and while the model reads them (and whatever the AI provider keeps under its own terms). The privacy page, terms and
the sub-processor list say so, and that the customer is responsible for their bucket's security, retention and
backups.

## 9. Key rotation and encryption at rest

For every secret we store: workspace AI keys and storage credentials now, later anything else (webhook secrets,
integration tokens). Based on OWASP's Cryptographic Storage and Key Management cheat sheets [O1, O2], NIST SP
800-57 Part 1 Rev 5 on key lifecycle and cryptoperiods [N1], and the envelope encryption model of Google Cloud KMS
and AWS KMS [K1, K2].

### 9.1 Envelope encryption

- Each stored secret gets its **own random 256-bit data key** (DEK, `crypto.randomBytes(32)`).
- The value is sealed with **AES-256-GCM** under the DEK, with a random 96-bit nonce and
  **AAD = `rocr:v1:<table>:<column>:<row id>`**.
- The DEK is **wrapped** with AES-256-GCM under the current key-encryption key (KEK), with its own random nonce and
  **AAD = `rocr:v1:<table>:<column>:<row id>:kek<version>`**.
- The KEK version belongs in the **wrap's** AAD, not the value's. If the value's AAD named the KEK version, rotating
  the KEK would mean re-encrypting every value, and re-wrapping only would no longer be possible.
- Each DEK seals one value, so the GCM limit of 2^32 random-nonce encryptions per key [N2] only bites on the KEK,
  which does one wrap per stored value: many orders of magnitude away.
- **Rotating the KEK re-wraps DEKs only** (small, fast, the value is never decrypted). A **DEK is replaced** whenever
  the value changes (a new key is pasted) and on suspected compromise.
- Stored format, one text column plus a `kek_version` column for counting:

  ```
  v1.<kekVersion>.<b64url(wrapNonce ‖ wrappedDEK ‖ wrapTag)>.<b64url(nonce)>.<b64url(ciphertext ‖ tag)>
  ```

  `v1` is the format version, so the scheme can change later without guessing.

- **Node `crypto` only** (`createCipheriv('aes-256-gcm')`, `randomBytes`). No new dependency. GCM tag checks are
  done by the cipher; anything we compare ourselves (fingerprints) uses `timingSafeEqual`. The DEK `Buffer` is
  `fill(0)`'d after use. The opened provider key is a JS string handed to the AI SDK and can't be zeroed; keep its
  scope to the one call.
- The row id is generated in the app before sealing (it's in the AAD); the repository refuses to open a value whose
  row's workspace doesn't match the caller's.
- Lives in `packages/core/src/secrets/` as `seal(context, plaintext)` / `open(context, sealed)` behind a `Secrets`
  Effect service. Errors carry a kind (`bad-format`, `missing-version`, `auth-failed`), never a value.

### 9.2 Where the KEK lives

| Option                                                                                                | For                                                                                                                       | Against                                                                                                                                                                                                                                          |
| ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **(a) `DATA_ENCRYPTION_KEYS` env var** (`2:<b64 32 bytes>,1:<…>`, current first; Vercel Sensitive)    | Simplest; no network call or new dependency; works the same on Vercel and Docker                                          | The KEK sits with the app: anyone who can read production env, or run code in it, can unwrap everything. A database dump alone is still useless                                                                                                  |
| **(b) Managed KMS** (Google Cloud KMS, since Gemini already needs a Google Cloud project; or AWS KMS) | The KEK never leaves the KMS; IAM, audit logs and rotation built in [K1, K2]; the usual answer on security questionnaires | A network call per unwrap (latency, a per-operation price, and a new outage dependency: if KMS is down, own-key reads stop). Needs a cloud credential in the app, which is itself a secret. Cache unwrapped DEKs in memory for at most 5 minutes |
| **(c) Supabase Vault**                                                                                | Built into our database host                                                                                              | The key then sits with the data provider, so one compromise of Supabase gets both. Ties us to Supabase                                                                                                                                           |

**Recommendation: (a) now, behind a `KeyProvider` interface** (`currentVersion`, `wrap(dek, aad)`,
`unwrap(version, wrapped, aad)`), so (b) is a drop-in implementation later and the stored format doesn't change
(`kekVersion` then names a KMS key version). **Move to KMS** when the first of these happens: a customer's security
review asks for it, the first contract that names key custody, SOC 2 work starts, or 50 workspaces use their own
key or storage. Not (c).

Startup rejects a malformed `DATA_ENCRYPTION_KEYS` (wrong length, duplicate versions) in `lib/env.ts`, like
`BETTER_AUTH_SECRETS`. Without it, BYOK and own storage are unavailable (Settings says so); the rest of the app runs.

**OAuth tokens.** Better Auth's `account.encryptOAuthTokens` is a boolean: it seals with its own `symmetricEncrypt`
under the auth secret, and 1.7.14 has no hook for a custom cipher (`dist/oauth2/utils.mjs`). We never read the
tokens (Google and GitHub are used for sign-in only). Better than moving them: stop keeping them, by clearing
`accessToken`, `refreshToken` and `idToken` in an `account` database hook (owner decision 14). Then rotating the auth
secret only signs people out, and no data depends on it.

### 9.3 Rotation jobs

Two job kinds in `packages/core/src/jobs`, both admin-started (or scheduled), audited, batched (100 rows, ordered by
id, cursor in the job payload so a crashed run resumes), idempotent:

- **`secrets.rewrap`**: for each registered sealed column, rows with `kek_version <> current`: unwrap the DEK with
  its version, wrap with the current one, then
  `update … set sealed = $new, kek_version = $cur where id = $id and sealed = $old`. Zero rows updated means the
  user changed it meanwhile (already current): skip. Values are never decrypted.
- **`secrets.reencrypt`**: same loop, but a new DEK and a full open/seal of the value. Used after a suspected leak.

A registry lists sealed columns (`ai_keys.sealed`, `workspace_storage.sealed`) so new ones join counts and
jobs by being added there.

### 9.4 Operations

**Scheduled rotation (yearly).** Cryptoperiod one year for the KEK, within NIST's guidance for key-wrapping keys
[N1] (exact table value to confirm). Steps for the runbook:

1. Generate 32 random bytes (`openssl rand -base64 32`), set `DATA_ENCRYPTION_KEYS=2:<new>,1:<old>`, deploy.
   New values use version 2.
2. Admin → Settings → Encryption → **Re-wrap now** (`secrets.rewrap`).
3. Check the counts: version 1 shows 0 values in every column, and "Safe to remove version 1" appears.
4. Set `DATA_ENCRYPTION_KEYS=2:<new>`, deploy.
5. Keep the old key in the password manager, marked retired, for 30 days (database backups older than the rotation
   still need it), then destroy it.

**Emergency rotation (suspected leak of env or database).** New KEK as above, then `secrets.reencrypt` (new DEKs, so
nothing derived from the old key survives), remove the old version as soon as counts are 0. Because a leaked env
means the **plaintext customer keys** may be out: mark every workspace key `failing`, email every owner to revoke the
key at Google or Anthropic and paste a new one, and the same for storage credentials. Platform keys in env are
rotated at the providers too. Incident note in the runbook.

**Admin → Settings → Encryption.** Current version; a table of columns × versions with counts
(`select kek_version, count(*) … group by 1`); "Re-wrap now" and "Re-encrypt now" (platform admin, confirm dialog,
audit row, shows job progress); "Safe to remove version N" when its count is 0 everywhere and N isn't current.

**Missing versions.** At startup, and in `/api/health`, compare the versions present in the registered columns with
`DATA_ENCRYPTION_KEYS`. Missing → health `degraded`, an error event (`secrets.version_missing` with the version
numbers), an Admin banner, and own-key features fail closed with a clear message. Not a refusal to boot: that would
take the whole app down over one feature, and would make a database blip at startup fatal. The **Database
Migration** workflow also runs the check before a deploy, so a deploy that drops a version in use stops there.

### 9.5 Tests

- Seal → open round trip; every format field present; wrong format version rejected.
- AAD swap: a value sealed for row A opened as row B (or another column) fails with `auth-failed`.
- Rewrap: values stay byte-identical after open; `kek_version` moves; running it twice changes nothing; a row edited
  mid-run is skipped, not overwritten.
- Reencrypt: DEK changes (wrapped part and ciphertext both differ), value identical.
- Missing version: a row with version 3 and env without it → health degraded, `missing-version` error, no plaintext
  or key bytes in the event.
- Canary: a fake key never appears in logs, events, errors or responses (§5.2).
