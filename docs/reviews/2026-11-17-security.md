## Low

### L1 · Receipts without a recorded size can stay uncounted for good. #291

`packages/core/src/jobs/kinds/receipt-file-size-backfill.ts:49-60` queues the backfill only if no job ever had the
key `receipt.file_size_backfill`, and `packages/core/src/jobs/retention.ts:27` keeps that first job forever, so the
backfill runs once in the database's life. `sumStorage` counts a null `file_bytes` as 0
(`packages/core/src/storage-quota.ts:13-15`). Two ways a row ends up null after that one run:

- During deploy skew, instances on the previous release keep inserting receipts without `file_bytes`. The new
  release's first drain can start (and finish) the backfill before the last old instance stops. The batch cursor is
  `id > after` over random v4 ids (`:87-92`), so a row inserted mid-run with a lower id is skipped too.
- If the first job dies (`storage-off` is non-retryable, `:159-160`), it is never queued again; only an admin
  re-run of that dead job recovers.

Impact: the cap undercounts by those rows, at most 10 MB each, for a handful of uploads in the skew window. No data
exposure. Fix: in `scheduleFileSizeBackfill`, queue a job (keyed by the current time bucket or release) whenever
`exists (select 1 from receipts where file_bytes is null and image_object_key is not null)` and no backfill job is
live, instead of "once ever"; keep the per-process flag. Add an integration test with a null row inserted after the
first job finished.

### L2 · A stored hash with out-of-bounds parameters is refused faster than a real check. #283

`apps/web/lib/password.ts:74-75` returns `false` without deriving when `parse` refuses the parameters, so that
account's wrong-password timing differs from an unknown address. Only a direct database edit can produce such a
row, and refusing is the right outcome. Optional: derive at `SCRYPT_PARAMS` before returning false. Not worth a
change on its own.

## Verified secure

**#291 storage cap**

- **The size is the server's, not the client's.** `fileBytes = input.body.byteLength` (`packages/core/src/pipeline.ts:204`),
  the same bytes passed to `storage.put` (`:214`); the multipart parser caps the body at `MAX_UPLOAD_BYTES`
  before this. No client field, header or `file.size` reaches `file_bytes`. Live: a 151-byte PNG sent as
  `type=application/pdf` with filename `../../evil.png` was stored with `file_bytes = 151`,
  `file_meta = {"contentType":"image/png","width":64,"height":64}`, and the key
  `users/<user id>/receipts/<receipt id>.png`; the name is kept only in `file_name`.
- **`file_meta` holds only server-derived values**: the sniffed type and `imageSize` of the bytes
  (`pipeline.ts:177-182`). `imageSize` always advances its JPEG offset and only reads inside the buffer.
- **Concurrent uploads can't pass the cap.** The workspace advisory lock is taken whenever a cap is set
  (`packages/core/src/repository.ts:612`), and the sum and insert run inside it (`:613-620`). Live: with 9,437
  bytes of room, six parallel 2,500-byte uploads gave exactly three 202s and three 429s; the workspace ended at
  99,998,063 of 100,000,000 bytes. Every stored object under the user's prefix has a row (15 and 15), so refused
  uploads left no orphans. Pinned by `receipts.int.test.ts:1009`.
- **A file over the room is refused** with 429 and no `Retry-After` (live, 10,000 bytes against 9,437).
- **One write path.** `ingestUpload` is the only caller of `storage.put` for receipts and `ReceiptRepo.insert` the
  only receipt insert; no route or action sets `file_bytes`, `file_meta` or `organization_id` on an existing
  receipt, and receipts are hard-deleted, so deleted rows stop counting.
- **Backfill HEADs are scoped by construction**: keys come from `receipts.image_object_key`, which only
  `receiptObjectKey` writes; the HEAD returns a size and nothing else, and the update never overwrites a size
  recorded at upload (`receipt-file-size-backfill.ts:113-116`).
- **Admin bounds.** `storageBytes` is an integer from 1 MB to 1 TB in the server schema (`packages/core/src/settings.ts:48-53`),
  defaults when absent from stored settings, and the form's MB-to-bytes conversion stays integral for decimal input.
  The sum is a `bigint` and stays below 2^53.
- **`DROP TABLE user_credentials`** (`apps/web/drizzle/0013_storage_cap.sql:8`): nothing in the code reads or
  writes it, nothing references it (its only constraint is its own FK to `user`), and no `CASCADE`. Applied locally;
  the table is gone and the two columns exist.

**#279 retention and scrub**

- **No live data is deleted.** Each purge selects past-period ids and repeats the predicate in the `DELETE`
  (`packages/core/src/retention.ts:27-37`), with periods measured by the database clock: sessions 1 day after
  `expires_at` (Better Auth refuses them at expiry), step-up events after 90 days (the lockout reads 15 minutes;
  the "last verified" read fails closed if a row is gone), invitations 30 days after `expires_at`, audit entries
  after 2 years. The only foreign keys into these tables are `step_up_codes` (cascade) and
  `step_up_events.session_id` (set null). No append-only trigger exists yet on `admin_audit_log` to conflict.
- **Contact-reply payloads are emptied on every terminal path.** `reap` when the job goes dead
  (`packages/core/src/jobs/queue.ts:334`), `cancel` (`:353`) and the admin `cancelQueuedJob`
  (`packages/core/src/jobs/admin.ts:188`), each returning the old payload for `onFinalFailure`; `rerunJob` refuses a
  scrubbed job (`admin.ts:75`). Kind names are bound parameters. The supersede cancels touch only `receipt.%`
  kinds. `attempt_log` holds outcome tokens, never messages. Pinned by `scrub.int.test.ts:83,97,104`.
- **Privacy page matches the code**: session and code retention, 90-day step-up records, invitations, job records
  (30 and 90 days; welcome rows kept while the account exists; their payload is a user id only), the auto-reply
  data "until it ends", the 2-year admin log, and the upload-metadata sentence (F9). The first `receipt.recheck` and
  `receipt.file_size_backfill` jobs are also kept indefinitely; they hold no personal data.

**#290 usage card**

- **Only the active workspace's usage is shown.** Every surface reads `getUsageSummary`, which takes
  `requireActiveScope()` (`apps/web/lib/quota.ts`), or the layout's usage for the same scope. The card shows the
  workspace's totals against its own plan, as the plan is per workspace; there is no per-member breakdown and no
  other workspace's figures. `meterAction` is a pure function of those values and the viewer's role.
  Live: switching the active workspace to one the user doesn't belong to is refused with 403
  (`USER_IS_NOT_A_MEMBER_OF_THE_ORGANIZATION`), and the second user gets 404 for the first user's receipt, its image
  and its delete.
