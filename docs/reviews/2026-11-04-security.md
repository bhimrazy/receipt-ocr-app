## Blocking

### B1 · A removed member keeps full read/write access to the workspace

- **Where:** `apps/web/lib/session.ts:70-71` (`getActiveScope` trusts `session.activeOrganizationId` without checking it
  against `member`). The comment at `:56-58` is wrong: Better Auth's `removeMember` only clears the active org on the
  *remover's* session (`better-auth/dist/plugins/organization/routes/crud-members.mjs:223`), and `leaveOrganization`
  only on the current session (`:436`).
- **Impact:** cross-tenant read, edit, delete, export and upload on every `/api/receipts*` route and in the
  history/receipt page loaders (`lib/receipts.ts:55,71`). This lasts as long as the removed user's session lives
  (7 days, sliding with daily refresh, so effectively for good while they keep using it). It is the exact case "remove
  the employee who left" is meant to handle. **High.**
- **Reproduction (done):** the owner invites the member, the member accepts and runs `set-active` on the owner's
  workspace, then the owner calls `POST /api/auth/organization/remove-member`. The DB then shows 0 `member` rows while
  the member's `session.active_organization_id` still equals the owner's workspace. Next, with the member's cookie:
  `GET /api/receipts/7e4397fc-…` → 200 with the owner's receipt; `GET /api/receipts/export` → 200 CSV of the owner's
  workspace; `PATCH /api/receipts/7e4397fc-…` `{"merchant":"changed-by-removed-member"}` → `{"ok":true}`, and the owner
  then sees the changed merchant. A fresh `set-active` to that org is correctly refused
  (`USER_IS_NOT_A_MEMBER_OF_THE_ORGANIZATION`), so only the cached session value is stale.
- **Fix:** make the scope structural. `getActiveScope` always resolves through
  `member WHERE user_id = session.user.id AND organization_id = activeOrganizationId` (one indexed query) and falls
  back to the first membership when there is no row. Optionally, also have a `member` delete hook clear
  `session.active_organization_id` for that user. Add a test: remove a member, then expect 404 from GET/PATCH/DELETE
  and an empty export.

### B2 · `ADMIN_EMAILS` grants platform admin to an unverified sign-up

- **Where:** `apps/web/lib/auth.ts:112-115` (role set in `user.create.before` from the claimed email), together with
  `:59-64` (verification is sent but never required). `.env.example:22-24` tells operators to list emails that "are
  auto-promoted … when they sign up", which is exactly the window.
- **Impact:** if any address in `ADMIN_EMAILS` has no account yet (fresh prod DB, or a second admin added later), anyone
  who `POST /api/auth/sign-up/email` with that address gets `role: "admin"`. That means the full admin panel,
  impersonation of any user, ban/remove, and every workspace's receipts. Ownership of the email is never proven.
  **High/critical in that window.**
- **Reproduction:** set `ADMIN_EMAILS=boss@corp.test`, then `curl -XPOST /api/auth/sign-up/email
  -d '{"email":"boss@corp.test","password":"x…","name":"x"}'`; the response has `"role":"admin"` and
  `"emailVerified":false`. Not run live: I can't set env on the shared server, and I don't read `.env`. The code path
  is unconditional.
- **Fix:** grant the role only once the email is verified. Drop the `before` hook. Instead, in `user.update.after`
  (when `emailVerified` flips to true) and in `user.create.after` (when the user was created verified, e.g. Google
  OAuth), promote if the email is listed. Add a test that an unverified listed sign-up stays `user`.

## Low

- **L1** `app/admin/users/[id]/page.tsx:53`: raw session tokens of the viewed user are serialized into the admin
  page's RSC/HTML (verified: the member's token appears in the `/admin/users/<id>` response). They aren't directly
  replayable: an unsigned token in the cookie or as a Bearer returns `null`, since the `bearer` plugin is off. They are
  still credentials sitting in the client. Pass `session.id` and resolve the token in the server action.
- **L2** `app/api/receipts/[id]/route.ts:62,112`, `export/route.ts`: there is no org-role check, so any `member` can
  edit or delete every receipt in the workspace. Decide whether that's intended. If not, gate mutations on
  `owner|admin` or the receipt's own `userId`.
- **L3** `lib/auth.ts:86-89`: the 5-min `cookieCache` means a banned user, or one whose sessions were revoked, keeps
  working for up to 5 minutes. After the B1 fix, membership is re-read per request, so this only affects ban/revoke.
  Acceptable, but document it, or use `disableCookieCache` on admin routes.
- **L4** `lib/env.ts:57`: `BETTER_AUTH_URL` silently defaults to `http://localhost:3000`. A prod deploy missing it gets
  localhost invite links, a `trustedOrigins` mismatch and non-`Secure` cookies. Throw in production when it's unset.
- **L5** `lib/auth.ts:159`: `requireEmailVerificationOnInvitation` is unset. Better Auth only skips the check
  because invitation IDs are opaque (`crud-invites.mjs:29-35`), and `list-user-invitations` already requires a
  verified email. Set it to `true` explicitly so a future `generateId` change can't reopen invite claiming by
  unverified accounts.
- **L6** `/api/receipts*` doesn't check `Origin`. A cross-origin `PATCH` with the owner's cookie returns 200
  server-side, and a `text/plain` body is accepted. Browsers are protected only by `SameSite=Lax` (verified on both
  cookies) and the JSON preflight. Cheap hardening: reject a non-matching `Origin` on non-GET.
- **L7** `lib/csv.ts:11`: the formula guard also prefixes negative numbers (`-5.00` → `'-5.00`), which breaks refunds in
  spreadsheets. Apply the guard only to text columns (merchant, category, item name).

## Known items (CTO U1–U9) — confirmed / refined

- **U3** confirmed (`route.ts:114`, `core/src/index.ts:447`). Refinement: an SVG is stored with
  `ContentType: image/svg+xml` (`storage/src/index.ts:47`), so opening the presigned URL runs script on the bucket
  origin. That's harmless to the app's cookies, but it's an XSS-hosting vector on your R2 domain. Also
  `fileName=".."` survives `receiptObjectKey` (`storage/src/index.ts:34`) as a literal `..` segment. It's still under
  `users/<id>/receipts/<uuid>/`, but key it by `<uuid>.<ext>` from the sniffed type.
- **U8** confirmed: `contact/route.ts:64-65` logs the email and message.
- **U9** confirmed and wider than contact: 8 sign-in attempts on one account with rotating `X-Forwarded-For` gave
  8×401 and no 429, while the same burst without XFF gave 429 on the 6th (rule `5/60s`). On Docker that means
  unlimited password guessing. Set `advanced.ipAddress.ipAddressHeaders` from an env var (empty unless behind a
  trusted proxy), and add a per-email limit.
- **U4** observation: right after sign-up the session has `activeOrganizationId: null`, because `session.create.before`
  runs before the `user.create.after` org insert. The `getActiveScope` fallback hides this, and the B1 fix keeps it
  working.
- U1, U2, U5, U6, U7 not re-examined beyond the above.

## Verified secure

- **Receipt queries are structurally scoped**: every repository read/write uses `scopeWhere(id, organizationId)` or
  `eq(organizationId)` (`core/src/index.ts:261-262,294,319,344,352,364,383,400,403`). The `receipt_items` delete
  (`:321`) runs inside the same tx after a scoped update. The gap is the *input* to the scope (B1), not the queries.
  There is no test pinning scoping yet; add one with B1.
- **`set-active` refuses non-members** (probed). `update-user` refuses `role` and `plan` (`FIELD_NOT_ALLOWED`, probed).
  Note: it does accept `emailVerified` in the body, but the value was not applied (still `false`).
- **Admin is enforced at three layers**: Better Auth admin endpoints 403 for a non-admin (`list-users`, `set-role`,
  probed). `/admin` returns 404 for a non-admin (probed). Every admin page (`users`, `users/[id]`, `organizations`) and
  every server action re-calls `requireAdmin()`, so partial RSC navigation can't skip the layout check.
- **Impersonation**: admins can't impersonate admins (no `impersonate-admins` in the default admin role,
  `admin/routes.mjs:589`). Sessions last 1 h and carry `impersonatedBy`. An impersonated non-admin can't reach admin
  endpoints.
- **Invitations**: acceptance requires a case-insensitive email match with the session user (`crud-invites.mjs:271`).
  Only an owner can invite with the `owner` role (`:125`).
- **OAuth linking**: implicit linking onto an unverified local account is refused (`link-account.mjs:140-141`). PKCE
  and state are Better Auth defaults.
- **Better Auth rate limits** use the database store. `request-password-reset` and `send-verification-email` return
  429 after 3 requests per 10 s (probed). Sign-in is limited to 5/60 s (subject to U9).
  `revokeSessionsOnPasswordReset: true`. Reset `redirectTo` is validated against `trustedOrigins` (403 for
  `https://evil.example` and `/\t/evil`).
- **Cookies**: `HttpOnly; SameSite=Lax`. `Secure` is derived from an https `baseURL`. The secret comes only from env,
  with a length warning (`env.ts:71`).
- **Presigned URLs**: a 10-min GET for a single key, signed only after a scoped DB lookup (`lib/receipts.ts:77-81`).
- **CSV export**: formula guard verified live (`=HYPERLINK(…)` exported as `'=HYPERLINK(…)`, quoted) and pinned by
  `csv.test.ts:59`.
- **No secrets in the client bundle**: client components import only types, `ai/categories` and `ui`. The only
  `NEXT_PUBLIC_*` is `NEXT_PUBLIC_SITE_URL`. API errors return tagged generic messages; provider detail goes to logs
  only (`route.ts:130,196`).
- **CI**: actions pinned to SHAs, `permissions: {}` at the top level, `persist-credentials: false`. No
  `pull_request_target` and no `${{ }}` interpolation into `run:` (PR number/URL passed via `env`). The Dependabot
  cooldown matches `bunfig.toml`.
