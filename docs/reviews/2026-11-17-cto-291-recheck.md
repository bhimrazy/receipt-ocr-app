## 1. Backfill (`packages/core/src/jobs/kinds/receipt-file-size-backfill.ts`)

- **Missing object → 0: correct.** A `StorageError` with `kind: "not-found"` becomes `bytes: 0` (`:106-109`). The HEAD maps a bare 404 to
  `ObjectNotFound` (`packages/storage/src/index.ts:107-110`), and that becomes `kind: "not-found"`
  (`packages/core/src/services.ts:125`).
- **No cursor: correct.** The select is `file_bytes is null and image_object_key is not null limit n` (`:47`, `:98`). The UPDATE
  writes only `where r.file_bytes is null` (`:120-122`), so every row it reads gets a value and a rerun changes nothing.
  The `payload.after` retention exception is gone (`jobs/retention.ts:22-25`).
- **Two-key follow-up: correct.** A run queues the other key (`:34`, `:157-160`). `jobs_idempotency_idx` is unique only
  over live states (`apps/web/drizzle/0000_baseline.sql:363`), so a finished key can be queued again, and a retry
  after the enqueue finds the follow-up already there. This is tested (`file-size-backfill.int.test.ts:157-174`).
- **First-drain scheduling: no double queue.** One `insert … select … where exists(unsized) and not exists(live
  backfill job) on conflict do nothing` (`:63-68`). Two processes racing hit the partial unique index. A dead job no
  longer blocks a restart, which is tested (`:192-208`). It runs once per process (`scheduled`, `:49`, `:69`), from
  `drainQueue` (`apps/web/lib/jobs.ts:107`).
- **Race with uploads: none.** The only receipt insert writes `fileBytes` in the same statement
  (`packages/core/src/repository.ts:621-631`), and the backfill never overwrites a non-null value.

**F1 · Medium: one permanently unreadable object stalls the whole backfill, and the stall comes back on every new process.**
`Effect.forEach` (`:101-112`) fails fast on any non-404 `StorageError`. That covers a 403, a 5xx that persists, and
`ContentLength` missing (`storage/src/index.ts:113`), which throws a plain `Error`. The failure throws away the sizes the
batch already read, and the UPDATE never runs. With no `ORDER BY` and no cursor, the next attempt reads the same rows
first, so all 5 attempts fail (`MAX_ATTEMPTS`, backoff 1 min to 1 h, `:22`, `:169`) and the job goes dead. Each new
process queues it again. That is bounded: one live job at a time, no tight loop, five attempts per process. But
every receipt behind the bad one stays `null`, so storage reads low for every workspace (null counts as 0,
`storage-quota.ts:10-14`), and on Vercel each cold start adds another dead job (failed jobs are kept 90 days).
*Fix:* run each HEAD with `Effect.either`, write the sizes that succeeded, and keep the failed ids for the rest of the
run (`and id <> all(${failed}::uuid[])` in the select). Fail retryable only when a batch makes no progress. Report
`counts.failed`. *Test:* a Storage layer whose `size` fails one key with a 500. Assert that the other rows fill and
that the run ends without looping.

**F3 · Low: the two-key chain can drop its follow-up.** If a run outlives its lease, or dies after its enqueue but before its
completion write, it is retried while its follow-up runs. Both can then enqueue while the other is still `running`,
both get `duplicate`, and the chain stops. The next process's first drain picks it up again
(`scheduleFileSizeBackfill`). *Fix:* none needed, because recovery is automatic.

**F4 · Low: the `exists(unsized)` checks scan `receipts` sequentially once the backfill is done** (`:66`, `:151-155`),
once per process and once per run. That is cheap at today's size. *Fix:* after `production-db` reports none unsized, add
a migration with `file_bytes NOT NULL` and delete the scheduler and the job kind.

## 2. Enforcement and the skipped-file flow

- **429 body: correct.** `failureResponse` returns `{error, kind: "storage", full}` with no `Retry-After`
  (`apps/web/lib/http.ts:93-99`). `storageFull` is set from `usedBytes >= limitBytes` (`storage-quota.ts:38-39`, `:64`).
  It is unit-tested (`tests/lib/http.test.ts:141-152`) and documented (`flows/upload-and-extraction.md:165`). This
  closes CTO L2.
- **The client maps it** (`lib/capture/upload-request.ts:42`). The queue marks the file `skipped`, which `start()` and `retry()`
  both leave alone (`batch-queue.ts:127-133`, `:201`, `:209`), and stops only on `full`. Both paths are tested
  (`tests/lib/capture/batch-queue.test.ts`, "skips a file that doesn't fit…" and "stops once storage is full…").
- **Scan is disabled only while `stoppedBy === "storage"` and the server's usage says full** (`upload-panel.tsx:673`,
  `:949`). After a run with no successes, `router.refresh()` fetches that state (`:528`). After a run with
  successes, the existing refresh does (`:537`). Leaving the page and coming back renders fresh usage. I found no
  permanent stuck state.

**F5 · Low: the file that hits `full` is marked "Doesn't fit" and can never be sent.** On `full`, the item that got the
refusal is `skipped` (`batch-queue.ts:128-129`; the test expects `["skipped","waiting"]`, `batch-queue.test.ts:200`),
so once there's room, Scan sends the waiting files but not that one. It doesn't fit no more than they do. The alert
says "add them once there's room" (`upload-panel.tsx:829`), but the waiting files only need Scan. With concurrency,
every in-flight file can come back `full` and each one fires its own toast as well as the alert. *Fix:* on `full`,
put the triggering item back to `waiting` (keep `skipped` for `no-fit`), toast only for `no-fit`, and change the copy to "scan them once there's room."

**F6 · Low: the full state goes stale across tabs.** If receipts are deleted in another tab, `noRoom` and the
`StorageFull` card (`:544`) stay until a reload or a navigation. *Fix:* call `router.refresh()` on `visibilitychange`
while storage is full.

## 4. `formatStorage` (`packages/core/src/plans.ts:91-100`)

- 0 → "0 MB". At the cap (100,000,000 B) → "100 MB", and one byte under → "99 MB", so used space never reads full
  early. 5 GB → "5 GB", and just under → "4.9 GB". Exact tenths are free of float error (the `node` check above).
- Refusal copy rounds the room left down and the file up (`storage-quota.ts:50-51`). Since down(left) ≤ left < file ≤
  up(file), a refused file never appears to fit.
- **F8 · Low: rounding up at a unit boundary prints the wrong unit.** 999,999 B → "1000 KB" (`:96`), and 999.9 MB → "1000
  MB" (`:98`). *Fix:* round first, then move to the next unit when the result reaches 1000. Add both cases to
  `storage-quota.test.ts`.

## 5. Migration 0013 guard (`apps/web/drizzle/0013_storage_cap.sql:9`)

Correct. Drizzle splits on `--> statement-breakpoint`, so the `;` inside the `DO $$ … $$` block survives. The
block's `IF EXISTS (SELECT 1 FROM "user_credentials") THEN RAISE EXCEPTION` aborts the migration transaction,
and the `SET LOCAL` lines (`:7-8`) apply to that same transaction. That was already the case and is unchanged. The
check takes ACCESS SHARE and the DROP then upgrades to ACCESS EXCLUSIVE. A write committed between them would be
dropped, but nothing writes the table. *Optional:* put `LOCK TABLE "user_credentials" IN ACCESS EXCLUSIVE MODE;`
before the check. This closes CTO L1.
