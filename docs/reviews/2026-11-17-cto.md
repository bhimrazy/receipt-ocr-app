## Findings

### Medium

**M1 (#283): rolling back past this PR locks out every user rehashed since the deploy.**
`apps/web/lib/auth.ts:318` swaps in `hashPassword`/`verifyPassword`. Every password set or signed in after the deploy
is stored as `$scrypt$N=…` (`apps/web/lib/password.ts:35-40`, `upgradePasswordHash` at `auth.ts:476`). Better Auth's
built-in verifier reads only `<salt>:<key>` (`password.ts:67`). `docs/deployment.md:355-360` says a code rollback is
"promote the previous production deployment" and "normally needs nothing else". After this PR that is no longer
true. Sign-in for those users fails until they reset their password, and nothing logs the cause. I didn't run Better
Auth's verifier against a new hash; this follows from the format.
*Fix:* add one line to the rollback section of `docs/deployment.md` and the runbook: "a deployment older than
#283 can't verify `$scrypt$` hashes; roll forward instead". A safer alternative costs two releases: ship the verifier
first, switch the hasher in the next release.

**M2 (#291): the backfill's cursor can skip rows, and a dead first job never runs again.**
`receipt-file-size-backfill.ts:86-92` walks `id > after order by id`. Receipt ids are random v4 UUIDs
(`pipeline.ts:212`). A row written without `file_bytes` by an old instance during rollout, with an id below the
cursor, is never revisited. `scheduleFileSizeBackfill` (`:49-61`) never queues the root key a second time, and
`jobs/retention.ts` keeps that first job forever. So a first job that dies (5 attempts, or `storage-off` at `:159-160`)
also ends the backfill for good, unless an admin re-runs it. The impact is an undercount (`null` counts as 0,
`storage-quota.ts:14`), not a wrong refusal. The cursor exists only because missing objects stay `null`
(`:99-101`).
*Fix (simpler):* write `file_bytes = 0` for a 404 and record the miss in `counts.missing` (and in `file_meta` if
needed). Then `where file_bytes is null … limit 100` moves forward with no cursor and no `after` payload. The follow-up
needs no key per cursor, and the rule that keeps the first job in `jobs/retention.ts` can go. A second run (for
example a versioned key on the next deploy) picks up the stragglers, and nothing has to be reasoned about.

### Low

**L1 (#291): `DROP TABLE "user_credentials"` can't be undone, and the migration doesn't check that the table is
empty.** `0013_storage_cap.sql:8`. The owner decided the drop (`docs/STATUS.md:266`) and grep finds no code that reads
or writes the table. Leaving out CASCADE and setting `lock_timeout = '3s'` (`:6`) is right. The drop also briefly locks
`"user"`, the table its foreign key references, and the 3 s timeout makes that fail rather than queue.
*Fix:* before the drop, add `DO $$ BEGIN IF EXISTS (SELECT 1 FROM user_credentials) THEN RAISE EXCEPTION
'user_credentials is not empty'; END IF; END $$;`. Or have the owner approve a read-only `count(*)` on `staging-db`
and `production-db` before step 6 of the release.

**L2 (#291): the storage refusal is a 429, which means "slow down".**
`errors.ts:23-31` and `http.ts:84-87`: `QuotaExceeded` with no `retryAfterSeconds`, so no `Retry-After` header.
The app's batch queue handles it correctly: no header means a wait over the limit, so it stops
(`batch-queue.ts:114-124`). A direct API client that retries on 429 will keep retrying a full workspace. Reusing the
error is still simpler than adding a new one.
*Fix:* keep 429. Put `kind: "storage"` in the JSON body (the wide event already has it) and document it next to the
upload API. Move to 403/409 only if an external client actually loops.

**L3 (#291): the cap check costs two aggregates per upload and serialises the workspace.** `pipeline.ts:207` (no lock)
and `repository.ts:612-618` (under the lock). With a cap set, every plan now takes the workspace lock. The PR's
`EXPLAIN` shows 8.9 ms warm for a 26,000-receipt workspace via a bitmap scan on `receipts_org_receipt_date_idx`. That
is acceptable. Lock order stays user then workspace (`usage.ts:156-165`), the same as `claimRetry`
(`repository.ts:743`). `integer` is the right type for `file_bytes`: one file is capped at 10 MiB
(`upload-limits.ts:4`) and the sum is cast to `bigint` (`storage-quota.ts:14`).
*Fix:* none now. If upload p95 rises, add `(organization_id) INCLUDE (file_bytes)` for an index-only sum.

**L4 (#291): nothing in the app shows storage used.** `formatStorage` is used only by pricing, plan copy and the admin
audit list (`git grep formatStorage -- apps/web`). A user first learns about the cap when an upload is refused.
*Fix:* add a storage line to the usage card or Billing (the product reviewer's call). `storageUsed` already exists
(`repository.ts:597`).

**L5 (#291, test gap): the follow-up chain is untested.** `file-size-backfill.int.test.ts:83-138` covers one batch
with 4 rows. Nothing checks the case past `BACKFILL_BATCH × MAX_BATCHES`, or a missing object at a batch boundary.
`backfillBatch(after, limit)` already takes a limit.
*Fix:* call `backfillBatch(null, 2)` over 5 rows with the 404 at position 2, then follow `last`. With M2's fix this
becomes "a rerun changes nothing".

**L6 (#279): the PR says "the indexes exist already". Three of the four don't.** The purges filter on
`session.expires_at`, `invitation.expires_at` and `step_up_events.created_at` (`packages/core/src/retention.ts:41-55`).
The only indexes are `session_user_id_idx` and `session_token_idx` (`auth-schema.ts:79`, `0000_baseline.sql:397-398`),
`invitation_*` on organization, email and inviter (`auth-schema.ts:174-177`), and `step_up_events (user_id,
created_at)` (`index.ts:787`), whose first column is `user_id`. Only `admin_audit_log_created_at_idx` (`index.ts:473`)
serves its purge. Each batch is a sequential scan, up to 20 a table a day (`maintenance-purge.ts:27-29`). That is fine
while the tables are small. `0008` set the precedent of indexing a purge's scan.
*Fix:* a follow-up migration (`0014`, after #291) with those three indexes, and correct the PR text.

**L7 (#279): the audit-log purge and the planned append-only trigger have to be designed together.**
`maintenance-purge.ts:113` deletes `admin_audit_log` rows older than 2 years. The security plan's P2-2
(`docs/plans/2026-11-07-security-incident-readiness.md:353`) calls for a trigger that refuses `UPDATE`/`DELETE`. The PR
body mentions this only under Rollout.
*Fix:* write down the trigger's shape now in data-protection.md Planned: `BEFORE UPDATE OR DELETE`; allow a
`DELETE` only when `OLD.created_at < now() - interval '2 years'`; refuse everything else. Add a test that asserts the
SQL period equals `ADMIN_AUDIT_RETENTION_YEARS`. Otherwise the period lives in two places.

The rest of #279 is sound. `purgeWhere` repeats the predicate in the `DELETE`, so a session refreshed between the read
and the delete is kept (`retention.ts:24-37`). `reap`/`cancel` return `old.payload` from a row-locked `FROM` subquery,
so `onFinalFailure` still gets the address (`queue.ts` diff). `rerunJob` refuses a scrubbed payload instead of running
`{}`.

**L8 (#279): STATUS is out of date.** `docs/STATUS.md:455-458` still says `maintenance.purge` "only purges
`support_messages`", and `:466-468` lists step-up retention as "Proposed". #279 doesn't touch STATUS.
*Fix:* update both items in #279.

**L9 (#283): the stored-parameter bounds are sound; the Bun runtime is not verified.** `password.ts:44-57`: N is a
power of two ≥ 2, r and p ≥ 1, `128·N·r ≤ 64 MiB`, `N·r·p ≤ 2^23` (about 10× the current 786,432 units). With these,
an edited row costs at most around 2 s of CPU and 64 MiB. `maxmem` (`:24`) allows twice that, so the bound is the only
limit. The compare-and-swap is correct: it re-checks the password against the hash it read (`password-upgrade.ts:32`)
and updates `where password = row.hash` (`:37`). Both races are tested (`password-upgrade.int.test.ts:97-131`). The
first sign-in of a legacy user pays about 340 ms more (a re-verify plus a new hash, by the PR's timings). That happens
once.
*Fix:* none in code. The Docker image runs Next on Bun (`docker/Dockerfile.prod:8`), and CI runs no test against it.
Before Docker matters, run a sign-in smoke test against the image once to confirm `scrypt` with `maxmem` behaves on
Bun.

**L10 (#290): the phone strip works out the plan from a nullable field.** `upload-panel.tsx:217-218` passes
`plan: plan.pro ? "free" : "pro"` and `owner: plan.offer === "owner"`, while the layout uses `scope.role === "owner"`
(`app/app/layout.tsx`). `:232` shows the action only when `plan.pro` is set. As a result, a Pro owner whose month is
used up sees "contact" on the card but nothing on the phone strip. I found no wrong offer for Free users.
*Fix:* put `plan: PlanId` and `owner: boolean` in `LimitPlan` (`app/app/page.tsx:212`) and pass them straight through.
