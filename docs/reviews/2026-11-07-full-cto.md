## 2. Findings

### High

**H1. An Anthropic request rejection reads as `bad-image`, which ends the chain and kills the receipt.**
`fromStatus` maps every 400 to `bad-image` (`errors.ts:34-44`). Google (`:54-67`), Groq (`:87-95`) and OpenAI
(`:125-135`) have body-aware branches; Anthropic has none, and `errors.test.ts:64-74` pins `invalid_request_error`
to `bad-image`, which stops the chain (`ocr.ts:157`) and kills the job (`receipt-extract.ts:60`). Sonnet 5.5 is
the default first step (`settings.ts:124`), so one rejection of the request itself (a schema keyword after an API
change, an `effort` value the model lacks once #111 lands, a retired id) fails every upload as "bad photo" without
reaching Gemini. *Fix:* `classifyAnthropic`: 400 from `api.anthropic.com` with `error.type ===
"invalid_request_error"` and no `IMAGE_COMPLAINT` match → `not-configured`; flip the test. Land before #111, which
is `CONFLICTING` with `main` (its `errors.ts` hunk duplicates #110).

### Medium

**M1. The gate is advisory and a flaky test took `main` red.** Run `42400279609` (push, #91) failed 2 tests in
`jobs.int.test.ts` and the 18:17 production deploy was skipped; the same test failed #108's run `42402252896`.
#109 fixed it (the drain tests assumed an exact split, `jobs.int.test.ts:367-378`). Red over 60 runs: 4/40 PR,
1/20 push; the other PR red was real (`seo.spec.ts:46`, `/privacy` description 165 > 160, fixed in #110).
Playwright runs with `retries: 1` in CI (`playwright.config.ts:16`), so e2e flakes pass unseen. *Fix:* require
`ci-ok` on `main` (owner); fail, or at least print, when the Playwright report has `flaky > 0`.

**M2. Groq and OpenAI are selectable in Admin without one live call.** No `groq`/`openai` file in
`bench/results/`; `extract.groq.test.ts` and `extract.openai.test.ts` mock the SDK; the classifiers encode assumed
error codes (`errors.ts:90-94,111-117`). *Smallest live smoke:* a `workflow_dispatch` + weekly workflow, keys as

$0.01; $1/month cap per console. `bench/ocr.ts` only prints at the end, so add `--require-success` (exit 1 on any
failed call).

**M3. The poll and the extraction guard load items and `raw_json` to read a status.** `GET /api/receipts/:id`
returns six fields (`[id]/route.ts:56-64`) via `repo.get` = `findFirst({ with: { items: true } })` plus a jobs
lookup for stale rows (`repository.ts:565-576`); `runExtraction` uses the same `get` only to compare `status` and
`attempts` (`pipeline.ts:245-249`). *Fix:* `repo.status(id, scope)`, a seven-column select, for both (11-06 P2-3).

**M4. Function-duration assumptions disagree.** `api/receipts/route.ts:32` and `retry/route.ts:17` set

and the next drain, which until pg_cron is set up (STATUS to-do) is the daily cron. Not verified on Vercel.
*Fix:* read the effective limit in the dashboard, derive both from one constant, notice on `job.tick` when
`duration_ms` is within 10 s of budget.

cannot yet rule out that Sonnet is safer on receipts this set lacks. M5 settles it.
